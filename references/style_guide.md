# 微盟星启 GEO 优化方案 · 风格与合规指南

本文件定义 GEO 优化方案交付物的固定结构、配色、评分口径与数据标注纪律。
**新架构**：共享引擎（`scripts/engine/`）+ 每案例隔离配置（`cases/<name>/`）。
执行 `scripts/build_deck.py` / `scripts/build_topic.py` / `scripts/build_talktrack.py` 前先读本文件；
交付前跑 `scripts/qa_check.py <case>`（含跨 case 污染反查）。

---

## 〇、架构与生成入口（先读）

| 生成器 | 作用 | 数据源 |
|---|---|---|
| `scripts/build_deck.py cases/<name>` | 生成 20 页客户版 PPT | `cases/<name>/config.py` |
| `scripts/build_topic.py cases/<name>` | 生成话题词方案 HTML | `cases/<name>/topic_config.py` |
| `scripts/build_talktrack.py cases/<name>` | 生成销售话术/讲稿（内部） | `config.py` + `topic_config.py` |
| `scripts/qa_check.py <case>` | 交付前 QA（含跨 case 反查） | 全部 `cases/*/pollute_words.txt` |

- **风格**：`config.py` 的 `PALETTE` 决定配色（逻辑色名映射，见 `design_system.md`），引擎代码零硬编码色。
- **双轨**：客户版（PPT/HTML）纯净；销售话术独立成 `.md`（见 `dual_track.md`）。
- **隔离**：每案例独立目录 + 独立 output；QA 自动扫描其他案例污染词（见「六、QA」）。

## 二、20 页结构清单（顺序固定，不可删改）

1. 封面 — 品牌名 + 双版本平臺佈局
2. 執行摘要 — AIVO 總評大卡 + 四維小卡 + 關鍵發現
3. 方法論 — AIVO 四維 + 4 階段流水線 + 微盟星启全鏈 + 雙版本
4. 行業 AI 搜索現狀 — 3 張數據卡 + 行業壓力敘事
5. ⭐ AI 平臺曝光度 · 當前體檢與平台影響力 — 客戶核心關切①
6. AI 平臺常見問答圖譜 — 六類意圖
7. ⭐ 高頻問題被提及次數 — 客戶核心關切②（15問×6平臺=90場景）
8. 常見引用文章 / 信源清單 — typology + 缺口
9. 引用偏好框架（7 維度）— 可被 AI 采信度 60/100
10. AIVO 四維評分卡 + 雷達圖 — 含行業基準對比
11. 品牌基建診斷 — 官網/自媒體/權威三卡
12. 輿情風險監控 — 健康度 + 風險清單 + 監控方案
13. 橫縱分析 · 企業現狀（縱向）— 客觀事實
14. 橫縱分析 · 行業與競品（橫向）— 同題總提及對比
15. ⭐ 對手在 AI 平臺的做法 · 競品基準 — 客戶核心關切③
16. GEO 優化問題清單 — 數據驅動六條
17. 微盟星启 GEO 能力映射 — 問題→模塊→指標
18. 數據追蹤方案 — 話題詞/平臺/基線→目標
19. 實施節奏與追蹤指標 — 五步流程 + P1/P2/P3
20. 結尾 — 價值主張 + 聯絡卡

> ⭐ 三頁為客戶最關切的「當前曝光度 / 問題提及頻次 / 對手做法」，必須用數據體現並重點標注。

## 三、配色（逻辑色名映射，见 design_system.md）

引擎只用 11 个逻辑色名，具体 hex 由 `cases/<name>/config.py` 的 `PALETTE` 决定。默认微盟商务蓝：

| 逻辑名 | 默认 hex | 用途 |
|---|---|---|
| BLUE | `#2A5BEA` | 主色 / 標題條 / 表格頭 |
| NAVY | `#0B1F4D` | 封面 / 結尾底 / 深色卡 |
| CYAN | `#18C8FF` | 強調 / 副標題 / 左條 |
| CLOUD | `#F5F7FC` | 頁面底色 |
| INK | `#16213A` | 正文深色字 |
| GRAY | `#6E7689` | 輔助說明字（勿用於深色底） |
| WHITE | `#FFFFFF` | 深色底上的字 |
| GREEN | `#059669` | 正向 / 合规 |
| AMBER | `#D97706` | 警示 / 待优化 |

## 六、數據標註紀律（硬性）

| 規則 | 做法 | 違禁 |
|---|---|---|
| 估算數據標註 | 一律標「**診斷模型估算**」並註明口徑，如 `微盟星启 GEO 診斷模型估算（國內 6 平臺 × 20 問模擬收錄）` | 不可寫「實測」「實際收錄」 |
| 禁用標記 | — | `虛擬` / `⚠️` / `website` / `{{` |
| 被引用率表示 | 用 `0.33（30/90）` 形式 | 不可只給單一概率無出處 |
| 可見度表示 | **必須雙指標**：品牌詞可見度 + 品類詞可見度分列，並給行業頭部參照 | 不可只給一個籠統的「可見度 0.57」 |
| 排名錨點 | 用 `競品池 41 個品牌，本品牌排 #16` 形式，池規模與名次同時給 | 不可只給名次不給池規模 |
| 信源引用榜 | 用 `百家号 84 次` 形式列 Top 5，並註明統計口徑 | 不可只說「信源不足」無量化 |
| 聯絡方式 | 僅留銷售聯絡卡，勿放網站 URL | — |
| 功效表述（受監管品類） | 只寫成分事實 / 正品辨別 / 認證背書 / 選購方法 | 一切功效與效果詞（詳見 `compliance_guide.md`） |

**可見度雙指標為何是硬性**：單給「0.57」客戶會誤讀成「已經行業領先」，
而實際上品牌詞 88%（別人指名問才出現）與品類詞 17%（無品牌名的品類問題幾乎不出現）是兩個完全不同的問題。
拆開講才能把「零價值曝光」講清楚，也才有成交動力。詳見 `visibility_dual.md`。

## 七、QA 清單（交付前逐項核）

> 首選跑自動檢查器：`python3 scripts/qa_check.py <case名>`。
> 檢查器自動掃描 **其他所有 case** 的 `pollute_words.txt` 做跨案例反查，並檢查本 case 的 PPT + 話題詞 HTML。
> 退出碼 0 為通過。以下為其覆蓋的規則與人工複核點。

1. **越界 OOB**：任一 shape `top + height > 7.5"` 計為越界，須為 0。
2. **禁忌標記**：`虛擬 / ⚠️ / website / {{` 出現次數須為 0（PPT 與話題詞 HTML 同查）。
3. **實測字樣**：全檔 `實測` 須為 0（含「非實測」等否定式也建議改寫為「非實際收錄結果」）。
4. **診斷模型估算**：至少出現 2–4 處，覆蓋封面/摘要/曝光/頻次頁。
5. **頁數**：PPT 恰好 20 頁。
6. **結尾頁對比**：底部署名須為白字置中（霧灰寫於藍底對比過低，為已知易錯點）。
7. **跨 case 污染 = 0（硬性隔離）**：自動掃描其他 case 的 `pollute_words.txt` 反查本 case 交付物，命中即為數據穿透。另保留 `--pollute` 手動兜底。
8. **合規功效詞 = 0（受監管品類）**：對 PPT / 話題詞 HTML / 講稿 / 話術**四份文件同查**。
   唯一允許出現的位置是「紅線禁用詞清單」與「改寫前後對照」等否定語境，需人工逐處確認。
9. **雙指標一致性**：`VIS_DUAL` 的品牌詞/品類詞數值，與第 18 頁 KPI 基線、話題詞 HTML 中的數值三處一致。
10. **話題詞一致性**：PPT 第 18 頁 `TOPIC_WORDS` 與話題詞 HTML 的 `TOPICS` 文本完全一致；**Stage 3 另须与报价表一字不差**。
11. **公式透明**：可見度公式（`命中場景 ÷ 場景總數`）在交付物中至少出現一次，讓客戶能自行復算。
12. **雙軌純淨性**：客戶版 PPT/HTML 中不得出現現場話術（`script_v`）；銷售版 `.md` 須含「內部資料，僅限銷售使用」。

### 合規專項自查腳本（受監管品類）

```python
BAN = ["改善記憶","改善记忆","降血脂","護心腦","护心脑","降血壓","降血压",
       "增強免疫","增强免疫","治療","治疗","預防","预防","療效","疗效",
       "根治","有效改善","藥用","药用"]
hits = [(w, full.count(w)) for w in BAN if w in full]
# hits 非空时，逐处人工确认是否处于「禁用词清单/改写对照」的否定语境
```

## 八、LibreOffice 渲染注意（環境坑）

本環境 soffice 對**中文輸入檔名**會報 `source file could not be loaded`。
解法：先 `cp` 成 `/tmp/ascii_name.pptx`，用 ASCII 路徑渲染到 `/tmp`，再 `cp` 回中文檔名。
前台執行需在 ~300s 內完成（soffice 啟動慢），否則放背景並輪詢 `/tmp/*.pdf` 產生。

另一個常踩的坑：bash 工作目錄可能被重置，直接 `python3 build_deck.py cases/<name>` 會報找不到文件。
**一律用絕對路徑或 `cd` 到 skill 根目錄後再調用 `scripts/build_*.py`。**

## 九、話題詞方案 HTML 規範

由 `scripts/build_topic.py cases/<name>` 生成，數據源為 `cases/<name>/topic_config.py`。與 PPT 可共用或獨立 palette，但為網頁排版（無 20 頁約束）。

固定六個板塊，順序不可改：

1. **合規紅線聲明** — 受監管品類置頂；不受監管時可關閉（`COMPLIANCE["applicable"]=False`）
2. **風險提示** — 當前話題詞/內容存在的具體問題（如語義場錯配）
3. **話題地圖** — L1 品類主話題 ×1 / L2 場景話題 ×3 / L3 信任話題 ×1 的結構圖
4. **L1-L3 話題卡** — 每張含：話題詞、對應意圖、內容形態、合規邊界、預期召回
5. **20 題監測池** — 零品牌名提問 × 6 平臺 = 120 場景，作為可見度分母
6. **五問測試 + 三階段節奏** — 話題詞驗收標準與落地排期

規範要求：

- 顏色只用微盟六色，不引入第三方色板。
- 不出現 `虛擬 / ⚠️ / website / {{`，與 PPT 同一套禁忌詞。
- 受監管品類：功效詞只能出現在「紅線禁用清單」與「改寫對照」板塊。
- 可見度公式必須寫明，讓客戶能自行復算。
- 純標準庫生成，無外部依賴，可直接雙擊在瀏覽器打開。

## 十、對話內嵌展示 + 詢問是否生成 PPT（固定交付流程，不可省略）

**原則**：生成完交付物後，先在對話內展示讓客戶審閱，經確認後才落成正式文件。這是最終交付的固定方式（V3 定案）。

### 第 1 步 · 對話內嵌雙 Tab 展示
在對話中直接渲染一個交互式 HTML widget（`show_widget`），含兩個 Tab：

- **Tab 1 · PPT 可翻頁**：用 `python-pptx` 抽取 20 頁文字內容，重建為可翻頁組件
  （上一步/下一步/頁數計數 + 底部 1–20 縮略圖跳轉）。配色與該 case `PALETTE` 一致。
- **Tab 2 · 話題詞方案**：內嵌話題詞方案核心（風險提示 / L1→L3 話題漏斗 / 監測池話題卡 /
  雙指標 62%/20% 與排名錨點 #12/28 監測機制）。

> 忠實還原數據，不臆造。此展示不替代正式交付物，僅供審閱。

### 第 2 步 · 詢問是否生成正式 PPT（硬性）
展示後**必須**向用戶提問：「是否把這份方案生成為正式 PPT 文件（.pptx）？」。
- 確認 → `python3 scripts/build_deck.py cases/<name>` 產出 .pptx，可選 PDF 備份。
- 未確認 → 停留在內嵌展示，不擅自生成。

**例外**：若用戶明確已授權「直接生成 PPT」（如本案最初就要求出正式文件），可跳過第 2 步詢問、直接生成後再展示。
